# Versioning

Crate and package versions are `X.Y.Z`. A **patch** (`Z`) carries fixes and
purely additive, backward-compatible features (for example a new reader);
existing outputs, wire formats, schemas and ABI symbols stay unchanged. A
**minor** (`Y`) carries any compatibility break: changed/removed API signature,
C ABI break or ABI version change (`N4FMT_ABI_VERSION`), wire/byte, normalized
record schema, persisted golden, `.n4a` payload or shared fixture change,
renamed ids, or changed decoded values of existing readers. `X` is the product
version. This repository classifies each of its bumps.

The C ABI has its own additive version, exposed at runtime via
`n4fmt_abi_version()` and as the compile-time constant
`N4FMT_ABI_VERSION` in `crates/nirs4all-formats-capi/src/lib.rs` (currently
`0.1.0`). Breaking ABI changes require a major ABI bump and migration
notes. The release pipeline ships the matching `nirs4all_formats.h` header
under `crates/nirs4all-formats-capi/include/`, regenerated by `cbindgen` on
every build of `nirs4all-formats-capi`.

The normalized record schema also carries a schema version so serialized
goldens and cached outputs can be migrated intentionally.

## Cross-repository version constraints

nirs4all packages from different repositories accept every patch of one tested
series, `>=X.Y[.Z],<X.(Y+1)`: Rust `"0.2"` (1.x: `">=1.4.1, <1.5"`, never
`"1.4"`), Python `>=0.2,<0.3` (1.x: `>=1.4.1,<1.5`), npm `^0.2.0` (1.x:
`~1.4.1`, never `^1.4.0`), R a lower bound plus a documented series. A patch
floor is allowed when a fix or feature from that patch is required; moving to a
new minor is an explicit, tested consumer decision. Exact, reproducible versions live only in
lockfiles (`Cargo.lock`, uv/pip locks, `package-lock.json`, hash-locked wheel
locks) and in the release order. The crates and bindings of this repository
(`nirs4all-formats`, `nirs4all-formats-core`, `nirs4all-formats-capi`, the
Python, WASM and R bindings) are versioned in lockstep by
`scripts/bump_version.sh`; their internal pins are not cross-repository
constraints. The vendored `nirs4all-hdf5-reader`/`nirs4all-netcdf-reader`
backports keep their exact `=0.9.3-nirs4all.1` pins because they are path
dependencies shipped from this repository.

Consumers (IO, Datasets, Core, Web, Studio) therefore never release just to
accept a Formats patch. The full policy is `docs/contracts/release/VERSION_CONSTRAINTS.md`
in `nirs4all-ecosystem`.

Enforcement in this repository: `scripts/bump_version.sh --check` and the
`version-sync`/`version-guard` workflows (lockstep and tag/manifest order),
the conformance goldens and record-schema version, and the cbindgen-generated
header. A guard that fails when a contract file changes without a minor bump
is not automated yet.
